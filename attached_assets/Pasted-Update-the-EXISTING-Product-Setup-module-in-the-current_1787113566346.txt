1. PLC / CLEARANCE STATUS MANAGEMENT
   ==================================================

The current application should NOT treat Aptos Price Status as the definitive PLC status.

The intended product lifecycle states are:

Current
EOL
Clearance

A product should NOT be created initially as Clearance.

Instead, PLC/Clearance status should be manageable AFTER the style/SKU already exists.

### Existing Product / Style View

Within the existing Product Setup experience, when a user opens an existing style/SKU, add a clearly accessible PLC Status area.

For example:

PLC Status
Current

[Change Status]

The current status should be clearly displayed as a lifecycle/status value rather than exposing the underlying Aptos pricing terminology.

Clicking "Change Status" should open a focused modal or side panel.

### Change PLC Status interaction

Show:

Style / Product
SKU
Current PLC Status
New PLC Status

Example:

Style:
WH-12345

SKU:
WH-12345-BLK-M

Current PLC Status:
Current

New PLC Status:
[ Clearance ▼ ]

[Cancel] [Update Status]

Available lifecycle statuses:

* Current
* EOL
* Clearance

Do not allow an initial product creation flow to select Clearance.

This action should be represented as a mocked future API action.

After clicking Update Status:

* Show a confirmation state.
* Update the displayed status in the UI.
* Show a small success notification such as:
  "PLC status updated successfully."
* The mock data should reflect the new state.

IMPORTANT DESIGN CONCEPT:

The application should conceptually treat the Style Master as the source of truth for PLC status.

Do NOT expose "Price Status" as if it is the same thing as PLC Status.

This distinction is important because Aptos Price Status is used for pricing and has historically caused ambiguity when determining PLC lifecycle.

2. PRODUCT IMAGES
=================

Add the ability to upload and view product/style images.

This should be integrated into the existing Product Setup rather than becoming a separate module.

Images are intended primarily as INTERNAL PRODUCT REFERENCE material for buyers and merchandise teams.

They are NOT ecommerce publishing assets.

This is particularly useful for products where visual reference is important when making buying/ranging decisions.

### Recommended UI

Add a new grouping/section called:

Images

Place it naturally within the existing Product Setup information architecture. If the current layout already has logical groupings, use the existing grouping conventions rather than introducing a completely new visual pattern.

The section should include:

Images

[ + Upload Images ]

Show uploaded images as a clean thumbnail grid.

Each image should support:

* Preview
* Remove/delete
* Filename
* Optional upload metadata if this fits the existing UI

Use realistic mock product imagery.

### Upload interaction

Clicking "+ Upload Images" should open a polished upload interaction.

Support the conceptual flow:

Select images
→ preview selected images
→ upload
→ images appear in the product gallery

Since this is a front-end prototype, mock the upload process.

Include realistic loading/progress behaviour if it fits the existing application.

### Image handling

The requirements indicate that vendor images may have inconsistent resolutions and file sizes.

Therefore the UI should communicate that uploaded images are automatically optimized/compressed.

For example, beneath the upload control:

"Images are automatically optimized for internal product reference."

Do NOT introduce unnecessarily strict image specifications because the exact final image standards have not yet been defined.

Images will ultimately be stored outside Aptos in the application's own image storage layer.

For this prototype, simply mock that behaviour.

3. INNER PACK / PACK UPC
========================

Add support for creating an Inner Pack / Pack UPC against an EXISTING SKU/style.

This belongs under the existing:

Logistics

grouping.

The business concept is:

A product can be sold as individual units but ordered, received and transported in an inner pack.

Example:

Water is sold as individual units.

Vendor order multiple = 6.

The vendor supplies an inner pack containing 6 units.

That inner pack has its own unique UPC.

The system needs to capture that Pack UPC and its relationship to the SKU/style.

### IMPORTANT FLOW RULE

Do NOT add Pack UPC creation into the initial SKU creation flow.

The reason is to avoid requiring multiple dependent APIs to execute sequentially during initial product creation.

Instead:

1. Create the SKU/style normally.
2. Open the existing SKU/style.
3. Go to Logistics.
4. Add/create an Inner Pack / Pack UPC.
5. Submit it through the separate interaction.

### Logistics UI

Within the existing Logistics grouping, add a section such as:

Inner Packs

or

Pack Information

Show existing pack configurations if available.

Example:

Inner Pack
Pack UPC: 050123456789
Order Multiple: 6
Units per Pack: 6
Status: Active

[ + Add Pack UPC ]

If no pack exists:

Inner Pack / Pack UPC

"No pack UPCs have been configured for this SKU."

[ + Add Pack UPC ]

### Add Pack UPC interaction

Clicking "+ Add Pack UPC" should open a modal or side panel.

Fields should include the concepts established in the discussion:

SKU / Style
Pack UPC
Order Multiple
Units per Pack

Use sensible labels and realistic mock values.

The exact final API field structure has not yet been confirmed, so do NOT invent a large number of additional fields.

Example:

Add Inner Pack

SKU
WH-12345-BLK-M

Pack UPC
[ 050123456789 ]

Order Multiple
[ 6 ]

Units per Pack
[ 6 ]

[Cancel] [Create Pack UPC]

After submission:

* Show a confirmation state.
* Add the pack configuration to the Logistics section.
* Show a success toast:
  "Pack UPC created successfully."
* Make it clear that this represents a separate future API operation.
